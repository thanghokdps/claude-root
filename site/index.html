Why

    
Fast code is easy. Trustworthy code takes a process.

    
Left alone, Claude Code skips the plan, stops mid-build to ask, commits to main, says "tests pass" without running them and forgets everything when the session ends. The kit fixes each of these, and makes the non-negotiable ones impossible to skip.

    

      
Without the kitWith the kitHandled by

Inside one build

    

      
Ask everything up front
Before the first edit, every open point is asked as options with a recommendation. After that Claude does not stop to ask: it settles a choice with a short debate and moves on.
ask-once · /resolve-question

      
A second pair of eyes on the plan
An agent that never saw the conversation checks the plan against the code: files exist, verify commands fail today, contracts match their callers.
plan review · up to 2 rounds

      
Each slice reviewed twice
Opus splits the work; each slice goes to the right engineer on a cheaper model. Two fresh reviewers check it: first "does it match the brief", then code quality.
spec ✅ → quality ✅

      
A report you can roll back
The build ends with evidence and a Decided for you list: every choice you did not make, why, and how to revert it.
/verify-done · Decided for you

    

    

      
What you get back
Every choice is listed, so nothing is decided silently.


✓ pnpm test — 48 passed · tsc — 0 errors

Decided for you
- reminder time zone → user's profile zone
  · why: src/users/model.ts:22 stores tz
  · revert: pass tz in the request body
- "due soon" → next 24 h
  · why: matches the digest window, jobs/digest.ts:8
  · revert: change DUE_SOON_HOURS

      
Always know where you are
The status line shows the model, branch, ticket, plan progress and how full the context is.


Opus · feat/412-reminders #412 · plan 3/5 add due-soon query · ctx 41% · normal


The lane picks the ceremony: tiny just does it, normal plans first, high-risk (auth, migrations, security, providers, public contracts) writes a spec and waits for your OK.

Guardrails

    
Rules that run, not rules that are remembered

    
A skill's text can be forgotten under pressure; a hook can't. Each one says why it stopped you, and none can crash the session.

    

      
Never from a session
Blocked outright.

        
branch-guardNo commit or push to main or an environment branch.

        
secret-guard.env*, keys and service accounts are never read or edited.

        
test-lockThe test that reproduces a bug can't be edited while it is being fixed.

        
release-gateA production mobile release ships only an approved release/<version>.

        
infra-gateProduction terraform, kubectl or helm applies are a person's.

        
edit-guardNo repo edits through sed -i or redirects, so lint and format see every change.

      

      
Waits for the process
The step can't happen until the work before it has.

        
ticket-gateA ticket's commit waits for its plan's skills and an approved plan review; its PR for /verify-done and review.

        
ask-onceNo questions once the build has started; the choice is debated and listed instead.

        
plan-gateA turn can't end quietly while the active plan has an open task.

      

      
Asks you first
Allowed, with your OK.

        
weakened-checkA commit that deletes a test, loosens an assertion or lowers a number in CONSTRAINTS.md.

        
sensitive-pathAn edit to CI, deploy config or Claude's own settings that the plan didn't name.

      

      
Keeps the context
Quietly helps the next turn and the next session.

        
repo-profileTells each session what the repo is and turns on its packs.

        
plan-recallBrings the active plan's next task back every turn, even after /clear.

        
learn-captureTurns what a session learned into lessons the next one reads.

      

    

  


  

    
Evals

    
Every change to the kit is tested

    
Four layers, cheapest first. The free ones run on every change; the paid ones run a real model in a sandbox and grade what it actually did.

    

      
free · every change0
Routing tests
One file per skill of plain-language prompts that must rank it in the top 3, so the right skill fires without a slash command.

      
free · every change0
Hook & script tests
Each hook is fed real tool-call JSON and must allow, ask or block exactly as documented.

      
real model · before a release0
Behaviour evals
Claude runs a real prompt on a fixture repo. Graders check which skill fired and an LLM judge checks the outcome: did it ask first, prove the command, leave the test alone.

      
real model · on demand5
Agent-code tiers
evalkit grades code an agent writes: tests, held-out and property tests that catch hardcoded answers, LLM rubric, lint and security.

    

    

      
Behaviour eval cases per plugin
Each case is a prompt, a fixture repo and graders.

      
Run them yourself
From a clone of the kit.


# free: lint, hook tests, routing, plugin validation
bash scripts/check.sh

# paid: one plugin's behaviour evals
bash scripts/eval-plugin.sh dev

# paid: before a demo, 3 runs, with vs without the kit
bash scripts/eval-plugin.sh dev --runs 3 --ablation with-without


What these runs find becomes a kit fix: #144, #145 and #149 came straight from them.

FAQ

    
Questions people ask first

    

      
Do I have to learn the slash commands?
No. Say what you want in your own words, in any language; the skill whose description matches fires. The commands are there when you want a specific one, and every README lists them.

      
Will it keep interrupting me with questions?
No. It asks everything it needs once, before the first edit, as options with a recommendation. After that it decides the small things itself and lists each one under Decided for you with the reason and how to undo it. It still asks before anything no rollback undoes: push, merge, deploy, delete.

      
Does it work with GitLab and Jira, or only GitHub?
All three. /breakdown creates tasks with glab, gh or the Jira connector; /ticket reads an issue from any of them; /finish-branch opens a PR or an MR; /sync-remote keeps a GitHub mirror and a GitLab origin in step. The team can also install the kit from GitLab.

      
What can it never do on its own?
Commit or push to main or an environment branch, read a secret file, edit the test that reproduces a bug while fixing it, ship a production mobile release or apply production infrastructure. Each is a hook that blocks the command and says why.

      
How do I set the quality bar for my repo?
Run /constraints. It measures where the repo is today and writes CONSTRAINTS.md: coverage of changed lines, type and lint errors, vulnerabilities, budgets, each with the command that checks it. /verify-done reports every row, and a commit that lowers a number asks you first.

      
What does an estimate from the kit mean?
A range with a stated basis: the files and tests the task touches, calibrated on this repo's merged PRs of the same shape. When the task ships, /ticket records the actual next to it and /retro turns the drift into the next calibration.

      
We already have a CLAUDE.md and team plugins. Do they clash?
Your project's CLAUDE.md and the plugins that cover your repo win; the kit says so in every skill that could overlap. The kit adds the process and the role engineers; it does not replace your conventions.

      
How much does it cost to run?
Less than running everything on the strongest model. Opus plans, decides and reviews; Sonnet writes code from an approved brief; Haiku does mechanical work. Every skill and every dispatched agent names its model, so the split is enforced, not hoped for.

      
I am a PM or QA, not a developer. Is there something for me?
Yes: hand over the requirement and read what comes back. /breakdown gives you tasks with Given/When/Then criteria and estimates you can challenge; every PR carries the ticket's intent, spec, plan review and evidence in plain text next to the code.
